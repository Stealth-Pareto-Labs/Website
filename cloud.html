Infrastructure  /  Cloud

Deploy in your own country.

Apps, jobs, databases, storage and the observability around them, running on the same nodes as the models they call. Not a region on another continent with your country’s name nowhere in it.

Get access What you can run

Your database, your retrieval and your model should be in the same building. Usually they are on different continents.

Why it matters

Distance is a tax you pay on every request.

A retrieval-augmented answer is not one call. It is an embedding, a vector lookup, a database read and a generation. Run those across an ocean and you pay the round trip four times, on every request, forever.

01

Latency that users feel

Co-locating the app, the data and the model removes the round trips that make an otherwise fast product feel slow to the people it was built for.

02

Data that stays

Residency is not a setting you tick. Your workloads and stores sit in the country you chose, under the law that already applies to your business.

03

One bill, one platform

Compute, storage and inference in the same project, with the same keys and the same access control, instead of three vendors and a VPN between them.

04

Built for anyone

A weekend project and a national system use the same primitives. There is no enterprise tier gating the useful parts.

What you can run

The primitives you already expect.

Nothing exotic, nothing you have to relearn. Containers, databases, queues, storage and the telemetry around them, with GPUs and models on the same nodes.

01

Compute

AppsAny registry image, autoscaled, optionally on GPUs with model weights cached on the node. Scales to zero.
StacksRoute one hostname across several apps and an external frontend, with custom domains and HTTPS.
JobsScheduled, one-off, parallel and GPU work, with retries and a run history.
FunctionsPull data from an API, a URL, a file or another store straight into your project’s database.
SandboxesIsolated microVMs for untrusted or generated code, started per run.
GPU jobsBatch work queued across the cluster for training, evaluation and bulk inference.
02

Data

PostgresManaged, with backups, a data explorer, a SQL console and a REST data API over your tables.
VectorEmbedding storage next to the models that produce it, so retrieval is a local call.
Key-valueA dedicated instance per store for caching, sessions and queues.
Object storageS3-compatible buckets, including public ones and static website hosting.
03

Observability

LogsPer project, searchable, with drains to your own sink and alerts on patterns.
MetricsInfrastructure and application metrics with alerting rules you define.
TracesAn OTLP endpoint and distributed traces, so a slow request can be followed across services.
04

Access and governance

OrganizationsInvite members by link, with roles and per-project membership.
API keysScoped to a project, for both the gateway and the platform API.
SecretsProject secrets, sealed so they can be written and used but never read back.
Policies and quotasOrganization-level rules and limits on what projects can consume.
SSHAccess to a project’s machines through per-project grants rather than shared keys.
Private cloudThe whole platform deployed on dedicated infrastructure for one organization.
Together

The cloud and the models are the same platform.

An app can hold a model’s weights cached on its own node. A job can run bulk inference without leaving the cluster. A vector store can sit beside the embedding model that fills it. That is the part a general-purpose cloud in another region cannot offer you.

Same nodes
Workloads run on the machines that serve the models, not across a public internet hop.
Same project
One set of keys, members and policies across compute, data and inference.
Same jurisdiction
Your app, your database and your model answer to the same law.
